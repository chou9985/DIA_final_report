Chapter 7: 專案風險管理 (Managing Risk)

風險定義：一種不確定的事件或情況，一旦發生，會對專案目標產生正面(機會)或負面(威脅)的影響。風險管理是「主動預防」而非「被動反應」。

1. 風險管理四步驟流程 (Risk Management Process)

  1. 風險識別 (Risk Identification):
    • 列出所有可能影響專案的風險（先看總體 Macro，再看細節）。
    • 工具：風險分解結構 (Risk Breakdown Structure, RBS) 結合工作分解結構 (WBS)、風險剖析 (Risk Profile，針對傳統不確定領域的提問清單)。
  2. 風險評估 (Risk Assessment):
    • 情境分析 (Scenario analysis): 評估機率 (Probability) 與 衝擊 (Impact)。
    • 失效模式與效應分析 (FMEA): 風險值 (Risk Value) = 衝擊 (Impact) × 機率 (Probability) × 偵測難易度 (Detection)
    • 機率分析：決策樹 (Decision trees)、PERT 模擬。
  3. 發展風險回應 (Risk Response Development): 針對負面與正面風險制定策略。
  4. 風險控制 (Risk Response Control): 建立風險登記表 (Risk Register)，監控觸發事件，執行應急計畫，並進行變更控制管理。

2. 風險與機會回應策略 (Response Strategies)

應對「威脅 (Threats)」- 負面風險 應對「機會 (Opportunities)」- 正面風險
  • Mitigating (減輕): 降低發生機率或減輕發生後的衝擊。
  • Avoiding (避免): 更改專案計畫以完全消除該風險。
  • Transferring (轉移): 轉嫁給第三方 (如：固定總價合約、買保險、外包)。
  • Escalating (上報): 超出專案經理權限，通報高層。
  • Retaining (承擔): 接受風險發生，不採取事前預防。
  • Exploit (開發/利用): 消除不確定性，確保機會100%發生。
  • Share (分享): 將所有權分配給最有能力捕捉機會的第三方。
  • Enhance (提高): 增加機會發生的機率或正面衝擊。
  • Escalate (上報): 通報高層此機會。
  • Accept (接受): 願意利用機會，但不主動追求。

3. 應急規劃與緩衝 (Contingency Planning & Buffers)

  • 應急計畫 (Contingency Plan): 不是初始計畫的一部分，只有在「風險觸發 (Triggered)」時才啟動的替代方案。缺乏應急計畫會導致決策延遲或恐慌。
  • 應急資金 (Contingency Funds):
    • 應急準備金 (Contingency reserves): 用於涵蓋「已識別」的風險，分配給特定工作包。
    • 管理準備金 (Management reserves): 用於涵蓋「未識別 (Unidentified)」的風險，應用於整個專案層級。
  • 時間緩衝 (Time Buffers): 用於吸收潛在延遲，常加在嚴重風險活動、容易延遲的合併活動 (Merge activities) 之後。

🤖 AI Prompting 指引：生成風險管理章節

請 AI 根據個案背景，執行以下任務：

  • Task 1: 使用 RBS 架構識別個案中的 5 個核心風險（需包含技術、排程、成本、資金等面向）。
  • Task 2: 製作「風險嚴重性矩陣 (Risk Severity Matrix)」，設定 1-5 分的機率與衝擊，計算 FMEA 風險值。
  • Task 3: 針對高風險項目，設計具體的「Mitigate」或「Transfer」策略，並清楚定義「觸發條件 (Trigger)」與「應急計畫 (Contingency Plan)」。
  • Task 4: 如果個案中有利多因素，請使用「機會管理 (Exploit/Share/Enhance)」提出建議。

Chapter 8: 資源與成本排程 (Scheduling Resources and Costs)

核心概念：網路圖的時間不算真正的進度表，直到「資源被分配」為止。成本估計也必須經過「時間定相 (Time-phased)」才能成為預算基準。

1. 專案限制分類 (Classification of Problem)

  • 時間限制型 (Time-Constrained Project): 完工日期不可變，資源可彈性增加。
    • 解決方案 - 資源平滑化 (Resource Smoothing): 利用正的寬裕時間 (Slack) 延遲非要徑活動，以削峰填谷，降低資源需求高峰。
    • 缺點：會減少寬裕時間，降低彈性，並產生更多要徑或近乎要徑的活動。
  • 資源限制型 (Resource-Constrained Project): 資源上限固定不可超額，時間可彈性延長。
    • 解決方案 - 資源平準化 (Resource Leveling): 資源不足時，延遲某些活動的晚開始時間 (Late Start)，導致專案總工期延長。
    • 排程啟發式法則 (Heuristics Rules，平行法): 當資源發生衝突時，決定誰先拿資源的順序：
      Rule 1: 最小寬裕時間 (Minimum slack) 優先。
      Rule 2: 最小持續時間 (Smallest duration) 優先。
      Rule 3: 最低活動識別碼 (Lowest activity ID) 優先。

2. 分割活動 (Splitting Activities)

指中斷某項工作將資源調走，之後再回來繼續。雖然可提高資源利用率，但會產生巨大的啟動與關閉成本 (Start-up / Shut-down costs)，實務上是導致專案延遲的主因，除非沒有啟動成本，否則應盡量避免。

3. 多專案資源排程 (Multiproject Resource Schedules)

共用資源會產生漣漪效應 (Ripple effect)、資源使用效率低下與瓶頸。解法包含：建立專案辦公室 (PMO)、使用優先佇列系統 (First come, first served)、外包、或聘僱臨時工。

4. 建立時間定相預算基準 (Time-Phased Budget Baseline)

為何需要？為了判斷專案是超前還是落後，以及預算是否超支。我們需要建立 計畫值 (Planned Value, PV) 作為評估已完成工作的基準。

🤖 AI Prompting 指引：生成資源與成本排程章節

請 AI 根據個案背景，執行以下任務：

  • Task 1: 判斷該個案是「Time-Constrained」還是「Resource-Constrained」？並說明判斷依據。
  • Task 2: 模擬一個資源衝突的情境（例如：專案中兩項任務同時需要同一台稀缺設備或關鍵人員）。請 AI 應用「啟發式法則 (Heuristics)」的 1, 2, 3 規則，逐步推演哪個任務應該先獲得資源，哪個任務必須被延遲。
  • Task 3: 討論在該個案中，如果採取「分割活動 (Splitting)」會產生哪些隱形的啟動/關閉成本？
  • Task 4: 說明該個案應如何建立 Time-Phased Budget Baseline 以便後續進行 EVM 追蹤。

Chapter 9: 縮短專案時程 (Reducing Project Duration)

趕工 (Crashing)：在正常時間之外，以增加成本為代價來縮短活動或專案工期的過程。

1. 加速專案的選項 (Options for Accelerating)

當資源不受限時 (Resources Not Constrained) 當資源受限時 (Resources Constrained)
  • 增加資源 (Add resources)
  • 將專案工作外包 (Outsource)
  • 排定加班 (Schedule overtime)
  • 建立核心專案團隊 (Core project team)
  • 做兩次 (先求快，再求好)
  • 提高團隊效率 (Improve efficiency)
  • 快速跟進 (Fast tracking): 將原本依序進行的活動改為平行 (平行作業)。
  • 關鍵鏈管理 (Critical-chain management)
  • 縮減專案範疇 (Reduce scope)
  • 降低品質標準 (Compromise quality)

2. 專案成本-時間圖 (Project Cost-Duration Graph)

  • 間接成本 (Indirect Costs): 無法直接歸屬單一工作包的成本 (如管理費、租金、罰款)。時間越長，間接成本越高。
  • 直接成本 (Direct Costs): 直接指派給工作包的成本 (如人工、材料)。時間越短 (趕工)，直接成本越高。
  • 目標：尋找「最佳成本-時間點 (Optimum cost-time point)」，即總成本（直接+間接）最低的工期。
趕工決策邏輯與公式

尋找可以縮短的活動條件：
1. 必須是要徑 (Critical Path) 上的活動。
2. 具有最低的趕工成本斜率 (Lowest Cost Slope)。

Cost Slope = (趕工成本 Crash Cost - 正常成本 Normal Cost) / (正常時間 Normal Time - 趕工時間 Crash Time)

3. 如果「成本」才是問題，而不是時間？

縮減範疇、讓業主承擔更多責任、外包給更便宜的供應商、腦力激盪節省成本的方案。

🤖 AI Prompting 指引：生成縮短時程 (Crashing) 章節

請 AI 根據個案背景，執行以下任務：

  • Task 1: 假設個案面臨「Time-to-market」壓力必須縮短時程。請 AI 提出 3 個在「資源不受限」下的加速方案，以及 2 個在「資源受限」下的加速方案 (例如 Fast tracking 的應用)。
  • Task 2: 建立模擬數據，列出 3 個要徑活動 (A, B, C) 的正常時間/成本與趕工時間/成本，並計算出它們的 Cost Slope。
  • Task 3: 根據 Task 2 的斜率，向老師展示團隊的最佳決策路徑 (先趕工斜率最低的活動，直到改變要徑或達到極限)。
  • Task 4: 討論趕工可能帶來的實際風險 (Practical Considerations)，例如喪失寬裕時間、品質下降。

Chapter 13: 專案進度與績效衡量 (Progress & Performance Measurement)

實獲值管理 (EVM, Earned Value Management) 是一種結合範疇、時程和資源來評估專案績效的強大方法。

1. EVM 核心三元素

  • PV (Planned Value, 計畫值): 基準預算。預計到目前為止應完成的工作的預算成本 (BCWS)。
  • AC (Actual Cost, 實際成本): 到目前為止，實際花費在已完成工作上的成本 (ACWP)。
  • EV (Earned Value, 實獲值): 到目前為止，實際已完成工作的預算價值 (BCWP)。 EV = (實際完成百分比) × (原始總預算 BAC)

2. 差異與指標分析公式總表 (Variances and Indexes)

類別 名稱 公式 判讀方式 (Interpretation)
變異分析 (Variances)
絕對金額		 成本變異 (CV) EV - AC 正值 (+) = 成本節約 ; 負值 (-) = 預算超支
時程變異 (SV) EV - PV 正值 (+) = 進度超前 ; 負值 (-) = 進度落後 (僅代表財務進度)
完工變異 (VAC) BAC - EAC 正值 (+) = 預期總花費低於預算 ; 負值 (-) = 預期總花費超支
績效指標 (Indexes)
效率比率		 成本績效指標 (CPI) EV / AC > 1.00 = 成本運用效率高 (每花1元創造大於1元的價值)
< 1.00 = 成本效率低
時程績效指標 (SPI) EV / PV > 1.00 = 進度超前效率高
< 1.00 = 進度落後

3. 預測完工成本 (Forecasting Final Project Cost)

  • BAC (Budget at Completion): 專案原始總預算。
  • EACre (Revised Estimated Cost at Completion): 現場專家根據新資訊重新評估的完工成本。
  • EACf (Forecasted Total Cost at Completion): 利用目前的 CPI 推算未來的完工成本。
    EACf = ETC + AC (其中 ETC = 預估剩餘工作成本 = (BAC - EV) / CPI)
  • TCPI (To Complete Performance Index): 為了在預算內完工，剩餘工作必須達到的成本效率。
    TCPI = (BAC - EV) / (BAC - AC) ；若 > 1，代表未來工作難以在剩餘預算內完成。

4. 其他衡量法則

  • 0/100 Rule: 工作包完成前實獲值為 0%，完成時給予 100% (適用於短天期任務)。
  • 50/50 Rule: 工作包開始即給 50%，完成時給剩下的 50%。

🤖 AI Prompting 指引：生成進度績效 (EVM) 章節

請 AI 根據個案背景，執行以下任務：

  • Task 1: 為個案設計一份「期中狀態報告 (Status Report)」。設定專案執行到第 X 個月，並虛構一組合理的 PV, AC, 實際完成百分比 數據。
  • Task 2: 根據 Task 1 的數據，計算出 EV, CV, SV, CPI, SPI，並以表格呈現。
  • Task 3: 解析這些指標的意義。例如：「目前的 CPI 為 0.85，SPI 為 0.9，顯示專案目前進度落後且成本超支。」
  • Task 4: 計算預測值 EACf 與 TCPI，並基於這些冰冷的數據，提出 3 個具體的管理行動 (Corrective Actions) 以挽救專案。

Chapter 14: 專案結案 (Project Closure)

專案結案是確保交付成果被接受、資源被妥善釋放，以及組織從中獲取經驗教訓的關鍵階段。

1. 專案結案的五種類型

  • 正常結案 (Normal): 專案按計畫完成。
  • 提早結案 (Premature): 產品提前交付 (可能刪減了部分功能以換取提早上線)。
  • 無止盡的專案 (Perpetual): 範疇潛變 (Scope creep) 導致專案不斷延長，需要強制結案。
  • 失敗的專案 (Failed project): 未達到技術或商業目標而終止。
  • 優先順序改變 (Changed priority): 高層策略改變導致專案被取消。

2. 結案六大核心活動 (Wrap-up Closure Activities)

  1. 獲得客戶的交付驗收 (Getting delivery acceptance)。
  2. 關閉資源並釋放給新用途 (Shutting down resources)。
  3. 重新分配專案團隊成員 (Reassigning members)。
  4. 結清帳戶並支付所有帳單 (Closing accounts)。
  5. 將專案(產品)交付給客戶 (Delivering the project)。
  6. 撰寫最終報告 (Creating a final report)。

3. 專案稽核與回顧 (Project Audits & Retrospectives)

  • 指導原則：稽核的哲學「不是獵巫 (Not a witch hunt)」，而是為了學習與保護組織資源。應對人類情緒敏感，數據必須可驗證。
  • 專案回顧 (Retrospectives): 透過獨立且受過訓練的引導者 (Facilitator)，使用問卷與一對一訪談，深入探討因果關係，並產出「經驗學習 (Lessons Learned)」。
  • 成熟度模型 (OPM3): PMI 開發的模型，分五級：初始 (Initial)、可重複 (Repeatable)、已定義 (Defined)、已管理 (Managed)、最佳化 (Optimized)。

4. 績效評估 (Performance Review)

  • 團隊評估：透過問卷衡量團隊如何共同工作、優勢與劣勢。
  • 個人評估：包含「發展 (Development)」(找出優缺點) 與「評估 (Evaluation)」(決定薪資)。
  • 360度回饋 (360-degree feedback): 從受其工作影響的所有人收集回饋。
  • 給予回饋的技巧：先請個人自我評估；避免與其他成員比較，應以既定標準評估；批評具體行為而非個人；保持一致且公平。

🤖 AI Prompting 指引：生成專案結案章節

請 AI 根據個案背景，執行以下任務：

  • Task 1: 定義該個案的結案情境（屬於正常完工、提早、還是失敗？）。列出團隊交付產品給客戶的具体验收標準 (Acceptance criteria)。
  • Task 2: 模擬「專案稽核報告 (Audit Report)」，寫出 3 點客觀的 Analysis (範疇/成本/時程達成率)，以及 2 點 Recommendations (技術或流程的改進建議)。
  • Task 3: 提煉出該專案的 3 個 Lessons Learned (經驗教訓)。明確指出在過程中犯的錯誤，以及未來類似專案應如何避免。
  • Task 4: 說明如何對個案中的團隊成員進行「績效評估」，並列舉在評估會議中會使用的 2 個良好溝通原則 (如：對事不對人、不與他人比較)。
